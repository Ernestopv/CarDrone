# MEMORY.md - CarDrone

## Project Context

- Frontend uses React + TypeScript + Vite.
- Backend will use .NET.
- Raspberry Pi GPIO config:
  - Pin1: 23
  - Pin2: 24
  - Pin3: 21
  - Pin4: 20
  - PWM1: 12
  - PWM2: 13
- Video will use uStreamer.
- Development order:
  1. Frontend
  2. Backend
  3. Raspberry Pi integration
  4. Video streaming

## Decisions Made

- Frontend must not know GPIO mappings.
- Drone commands are semantic: FORWARD, BACKWARD, LEFT, RIGHT, STOP.
- Hardware control will be abstracted behind the .NET backend.
- Initial frontend uses mock data only.
- No emergency stop control in the UI: STOP is the only stop mechanism.
- Requested vs confirmed command: the UI sets `requestedCommand` optimistically; only a `DroneService` acknowledgement updates `confirmedCommand` (simulated in Phase 1, never hardware).
- Speed validation by layer: the frontend clamps `0-100` (client-side convenience), the backend domain rejects out-of-range values with `ArgumentOutOfRangeException` (authoritative invariant; the API maps it to an error response later).
- Backend drone simulator (Task 11): `MockDroneController` lives in `DroneControl.Infrastructure` (adapter behind the Application contract, next to the future hardware implementation) and is registered as a singleton because it owns the simulated state across requests. Delays mirror the frontend mock as named constants: 700 ms connect, 250 ms command acknowledgement. `DroneNotConnectedException` (Application) is the detection contract for commands while disconnected — deliberate divergence from the Phase 1 frontend mock, which silently resolves; speed while offline stays a no-op (parity). A disconnect supersedes in-flight connection attempts and confirmations via an epoch counter.
- Backend HTTP contract (Task 12): endpoints return the domain `DroneStatus` as-is — camelCase property names plus lowercase enum values, configured once in the API layer (`JsonStringEnumConverter(CamelCase, allowIntegerValues: false)` on MVC JSON options; numeric enum values are not on the wire). The response deliberately has no `failedCommand` and no `services` grouping: the frontend service abstraction adapts to its UI shape in Tasks 18/19. Validation split: Task 12 owns input validation (missing/unknown `command`, missing/out-of-range `speed`, malformed JSON → 400 via `ValidationProblem`); execution failures (`DroneNotConnectedException` etc.) are deliberately unmapped until Task 16 — interim status is 500, documented as a gap, not a contract.

- Backend container (Task 13): `backend/Dockerfile` is multi-stage - `mcr.microsoft.com/dotnet/sdk:10.0` builds (four `.csproj` files copied first for a cached restore layer, then Release `dotnet publish --no-restore` of `DroneControl.Api`), `mcr.microsoft.com/dotnet/aspnet:10.0` runs. Publish is framework-dependent with no RID and the Dockerfile has no `--platform` pin, so the same file builds `linux/amd64` and `linux/arm64` in Task 15. Final local image `cardrone-backend` (~231 MB, runtime-only): `USER app` (non-root), `EXPOSE 8080` (ASP.NET container default), host mapping `5080:8080`, `ENTRYPOINT dotnet DroneControl.Api.dll`. Deliberately no `HEALTHCHECK` instruction - the aspnet image ships no probe tooling, so probe orchestration against `GET /api/health` belongs to Task 14's Compose file. Environment-variable configuration is observably effective: `GET /openapi/v1.json` returns 404 by default (Production) and 200 with `docker run -e ASPNETCORE_ENVIRONMENT=Development`. `backend/.dockerignore` excludes `**/bin`, `**/obj`, `**/.vs`, and Docker/Compose files (build context ~33 kB). Container tasks require the Docker daemon with a Linux engine (Docker Desktop) running.

- Docker Compose dev environment (Task 14): root `docker-compose.yml` with exactly one service `backend` (`build: ./backend` + `image: cardrone-backend`, ports `5080:8080`, `ASPNETCORE_ENVIRONMENT=Development`) and a Compose-level `healthcheck`; the Dockerfile keeps no `HEALTHCHECK` (Task 13 decision preserved). Probe mechanics: `CMD bash -c` performs a raw HTTP GET to `/api/health` via bash `/dev/tcp` and requires the `200` status line - the `aspnet:10.0` image has sh/bash/grep but no curl/wget (verified by running the image). Two gotchas learned: (1) Compose interpolates `$var` inside YAML values, so the healthcheck script needs `$$line` escaping - `docker compose config` caught the silent corruption; (2) Docker Engine 29 no longer exposes the probe as `.State.Health.Test` (state now only has Status/FailingStreak/Log) - read the configured test from `.Config.Healthcheck.Test`. The healthcheck makes the service report `healthy` ~10 s after `docker compose up -d`; root `.gitignore` excludes `.env` as the secrets pattern for future `${VAR}` interpolation; `depends_on`/`service_healthy` deferred until a second service exists.

- Multi-arch builds (Task 15): cross-arch builds need QEMU/binfmt registered first - `docker run --privileged --rm tonistiigi/binfmt --install arm64` (throwaway; lost on Docker Desktop VM restart, so `exec format error` means re-register), verified by `docker buildx ls` listing `linux/arm64` and an arm64 `alpine uname -m` -> `aarch64`. The `docker` driver **cannot write OCI output** ("OCI exporter is not supported for the docker driver"), so the combined `--platform linux/amd64,linux/arm64` build requires a dedicated `docker-container` builder: `docker buildx create --driver docker-container --use` -> build `--output type=oci,dest=...` -> `docker buildx rm --force` (bare `rm` prompts for confirmation). All build commands are documented and audit-validated in `docs/DOCKER.md`. Timings on this host: arm64 cross-build ~5.6 min, cold combined build ~10-11 min; Task 13's Dockerfile is byte-identical (SHA256 FB0903F4...) and amd64/arm64 images have identical config (same Entrypoint/ExposedPorts/`USER app`). Validation tags `:amd64`/`:arm64`, the OCI tarball, and temp builders are throwaway - only `cardrone-backend:latest` persists for Compose.

- Backend error handling (Task 16): the execution-failure mapping Task 12 deferred is live. Pipeline: `AddProblemDetails()` + `AddExceptionHandler<DroneExceptionHandler>()` + bare `app.UseExceptionHandler()` (first user middleware, so it pre-empts the auto-inserted developer exception page and returns ProblemDetails JSON in every environment - stacks go to logs only). `DroneControl.Api/Errors/DroneExceptionHandler.cs` maps `DroneNotConnectedException` -> 409 and the new reserved `DroneUnavailableException` (Application; nothing throws it yet - it is the hardware phase's detection channel) -> 503, warning-logged; everything else returns false and falls through to the default generic 500 (middleware logs it). Wire statuses: 400 input validation (Task 12 shape, unchanged), 409 command-while-disconnected, 503 implementation unavailable, 500 unexpected. Gotcha: `ExceptionHandlerMiddleware` pre-sets status 500 before invoking handlers and `IProblemDetailsService` never changes it - a custom IExceptionHandler must assign `httpContext.Response.StatusCode` itself before writing the body (the ProblemDetails `status` member alone leaves the wire at 500). Production runs for validation need `dotnet run --no-launch-profile` or launchSettings silently forces ASPNETCORE_ENVIRONMENT=Development.

- Backend tests (Task 17): `backend/tests/` has three xUnit projects (Domain.Tests 9, Application.Tests 27, Api.Tests 15 = 51 tests) added to the solution; packages are strictly Test.Sdk + xunit + runner (+ Microsoft.AspNetCore.Mvc.Testing 10.0.12 in Api.Tests; the template's coverlet.collector was removed to keep the whitelist). No mocking library — hand-written fakes: `FakeDroneController` (recording, Application.Tests) and `ScriptedDroneController` (throwing, Api.Tests). The only production touch is `public partial class Program { }` at the end of Program.cs (WebApplicationFactory seam). Conventions: simulator timing tests assert lower bounds only (600/150 ms floors for the 700/250 ms constants), never upper bounds, no Thread.Sleep — and `dotnet test` must pass twice consecutively (determinism gate). Api.Tests share the WAF host's real singleton simulator, so state-sensitive tests start with `await factory.ResetAsync()` (POST disconnect is unconditional and immediate). DI override trick for mapping tests: `ConfigureServices(services => services.AddSingleton<IDroneController>(fake))` — last registration wins over Program's real one. The 503/unexpected-500 mappings from Task 16 are now covered permanently (they were only throwaway-harness-verifiable before).

- Frontend API drone service (Task 18): `ApiDroneService` (`frontend/src/services/apiDroneService.ts`) is the only module allowed to call `fetch`; UI keeps importing `droneService`/`scenarioService` from `services/droneService.ts`, where `VITE_DRONE_SERVICE` selects the implementation — 'mock' remains the default until Task 19 flips it — and `VITE_API_BASE_URL` (default `http://localhost:5080`, trailing-slash trimmed) sets the backend origin. Wire→UI mapping: connection/camera/requested/confirmed/speed pass through; `connected`/`streaming` derive `services.*: 'online'` (unknown values fail safe to 'offline'); `failedCommand` is always null (no wire concept — failures arrive as HTTP rejections the hook already reloads status for). Ack honesty: `sendCommand` can only ever resolve `{ source: 'simulated', confirmedByHardware: false }`; the wire has no acknowledgement-source field and a future hardware-phase spec must extend it before the frontend could claim hardware confirmation. Command-while-disconnected rejects via the backend 409 (deliberate divergence from the mock's silent no-op). In 'api' mode `scenarioService.runScenario` rejects explicitly ("API-backed") instead of touching orphaned mock state. `vite-env.d.ts` was added (first-ever `import.meta.env` use); `frontend/.env.example` documents both variables; `.env` stays excluded.

- Frontend connected to backend (Task 19): `VITE_DRONE_SERVICE` default is now **'api'** (unset → ApiDroneService against `VITE_API_BASE_URL`; 'mock' is the documented opt-out for backend-less UI development, any other value also falls back to mock). `droneService.ts` exports `supportsMockScenarios` — App.tsx renders the MockScenariosPanel only under mock selection (scenario triggers would otherwise fake failures against a real backend), the hook's `runScenario` is a silent no-op guard in api mode, and Task 18's rejecting scenarioService remains as defense-in-depth. `useDroneDashboard` gained a startup `getStatus()` load (the backend simulator is a reload-persistent singleton — the UI shows truth or the existing error state, never a guess). Vitest `setup.ts` pins `import.meta.env.VITE_DRONE_SERVICE='mock'` before any module import so all pre-existing suites stay simulator-behavior tests; API-mode suites stub env explicitly (vi.stubEnv captures 'mock' as the original → unstubAllEnvs restores the pin). 121 frontend tests; live E2E + CORS preflight (`OPTIONS` → 204 + `Access-Control-Allow-Origin: http://localhost:5173`) verified against the running API with zero backend changes.

- Full-stack compose (Task 20): root `docker-compose.yml` now runs the whole app - backend (unchanged Task 14 block) plus a new `frontend` service built by `frontend/Dockerfile` (`node:22-alpine` `npm ci`+build -> `nginx:1-alpine` static + `/api/` proxy to `http://backend:8080`). - Hardware abstraction (Task 22): `IDroneHardware` (Application) is the three-member seam below `IDroneController` — `GetAvailabilityAsync` → `HardwareAvailability {Unavailable=0, Available}`, `ExecuteCommandAsync(DroneCommand)` → `CommandExecutionResult(HardwareCommandStatus {Rejected=0, Applied}, Reason?)`, `ApplySpeedAsync(0-100)`. Zero-valued enum members are the PESSIMISTIC states (unset never reads as Available/Applied). Contract rules pinned by the interface XML docs + tests: unreachable hardware throws the existing `DroneUnavailableException` (never silent no-op — D5); `Applied` is software-level only and can never mean physical actuation confirmation (hardware confirmation stays blocked on the wire-contract extension in Task 21's prerequisites ledger); speed rejects out-of-range (never clamps); every operation honors its CancellationToken. `MockDroneHardware` (Infrastructure) is immediate/deterministic/static-free/always-available with last-command/last-speed introspection properties. Task 22 wired NOTHING: Program.cs/DI byte-identical (no consumer until Task 23's config-based selection); `MockDroneController` untouched (coexistence decided later by Tasks 23/35). Vocabulary-purity rule (grep-verified): no Gpio/Pin/PWM/L298N/device-path words in Application sources. Application.Tests 27→40 (13 new); solution totals 9+15+40=64, deterministic across consecutive runs.

- Raspberry hardware provider + runtime mode selection (Task 23): composition-root helper `DroneRuntimeSelection.AddDroneRuntime` (Api — the only platform-aware spot) parses `HARDWARE_MODE` once (unset/null → mock; present-but-empty = invalid → abort; case-insensitive trimmed values `mock|dry-run|real`); `real` passes an OS/arch preflight (Linux+Arm64 via RuntimeInformation — OS facts only, NO device probing — that's Task 24) else throws `HostAbortedException`; `dry-run` behavior is documented under Task 27 below. `real` registers `RaspberryDroneHardware` (inert by design: always Unavailable, ops throw `DroneUnavailableException` — wiring is unverified until Task 28, so any actuation would be invented) + `HardwareDroneController : IDroneController` bridge (probe-gated connect, request-intent only until `Applied`, honest `camera: Offline`, raspberryPi field = probed availability, offline speed no-op parity, range invariant first). Verified: mock-tested (91 backend tests), `linux/arm64` BUILD verified — Pi runtime NOT VERIFIED (no hardware). Gotcha confirmed live: binfmt dies with a Docker VM restart; re-run the documented `tonistiigi/binfmt --install arm64` before arm64 builds, and `docker compose build` after source changes or `up` runs stale images.

- Hardware fail-safe (Task 26): `DroneSafetyController` decorates the selected `IDroneController` and is started/stopped by an ASP.NET hosted-lifecycle adapter. It owns software states `Unverified/Safe/CommandActive/StopPending/Faulted/Recovering`, serializes operations, applies validated bounded command/STOP/recovery deadlines, cancels and supersedes watchdog leases, routes semantic STOP through the same inner controller, and logs structured reason categories. `Safety:*` settings live in appsettings/Compose with bounded validation. Startup establishes a software baseline (connect→STOP→disconnect); failure leaves the host serving health but safety Faulted, so movement rejects. Graceful shutdown makes a bounded STOP attempt. Crucial D7 gate: `Safety:ExternalAbruptFailureProtectionVerified=false` by default; `HARDWARE_MODE=real` performs no controller operation and remains faulted unless an operator explicitly asserts that an external abrupt-failure mechanism has separately been verified. That flag is NOT proof; no watchdog/electrical mechanism is implemented or claimed. Backend safety tests use fakes only; physical stop remains NOT VERIFIED.

- GPIO abstraction (Task 25): Infrastructure defines `IGpioController`, `IRaspberryGpioPlatform`, output-only `GpioPinMode`, transport-level `GpioPinValue.Low/High`, `GpioPinConfiguration.FromSection` (required Pin1–Pin4; rejects missing/malformed/negative/duplicates; optional verified supported-ID set; ignores PWM1/2), deterministic `MockGpioController`, and `RaspberryGpioController` as a thin delegator to the platform port. No concrete Linux API/device path/library is selected; target-specific runtime values and physical GPIO access are explicitly deferred and do not block Task 25 completion. The fake platform tests forwarding, exception/cancellation propagation, and disposal. No motor/electrical semantics or Raspberry runtime claim.

- Hardware dry-run mode (Task 27): `HARDWARE_MODE=dry-run` now passes the same Linux+Arm64 preflight as `real` and registers the identical hardware flow (`RaspberryDroneHardware` + `HardwareDroneController`) plus a startup `GPIO` config preflight (new `GPIO` section in appsettings carrying the documented identifier values — still target-unverified per Task 24 — and `PWM1/PWM2` present but unconsumed) and `IGpioController → DryRunGpioController`. The dry-run sink is the lowest output boundary: it validates exactly like the mock, emits a structured `DryRunOperationRecord` (category GPIO/PWM-vocabulary, identifier, requested parameters, sequence, timestamp, `dryRun=true`, `physicallyApplied=false`, suppression reason — never "confirmed"/"acknowledged") BEFORE suppressing, holds no reference to any real platform sink (structurally unreachable; plus a composition guard that aborts startup if `IRaspberryGpioPlatform`/`RaspberryGpioController` is already registered → "Unsafe composition"), and is fail-closed: a record/log failure throws with no state committed and no physical fallback, and in the safety flow that leaves the Task 26 path Faulted. Real mode registers no GPIO sink yet (concrete Linux API still deferred). Dry-run is NOT D7-gated (nothing in the graph can energize); it starts Faulted today because the provider stays inert until Task 28 — spec-conformant ("provider failure → existing unavailable behavior"). Test seam: internal `AddDroneRuntime(configuration, raspberryRuntimeSupported)` exposed via `InternalsVisibleTo("DroneControl.Api.Tests")` so composition graphs resolve on a PC; the public entry always runs the real OS/arch check.
